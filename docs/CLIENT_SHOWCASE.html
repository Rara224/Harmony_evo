把 HarmonyOS 调试经验接进开发现场

Harmony_Evo Client 通过 Claude Code hooks 和 OpenCode MCP，把服务端案例资产、开发事件、失败证据和反馈数据串成一个闭环，让案例库从“静态文档”变成“开发中可复用、可沉淀、可审核”的共享资产。

Claude Code hooks 已验证 OpenCode MCP + Hook 已验证 事件级 dev-signal 已实现 候选案例默认不自动提交

一页接入方式

1. 启动服务端

在 Harmony_Evo 项目目录启动共享资产服务。

cd /Users/ra/Downloads/Paper_Repo/Harmony_Evo
npm run server

2. 接 Claude Code

在业务 HarmonyOS 项目目录安装项目级 hooks。

node /Users/ra/Downloads/Paper_Repo/Harmony_Evo/clients/harmony-evo-client/bin/harmony-evo-client.js install claude --server http://localhost:3456 --upload-signals

3. 接 OpenCode MCP + Hook

在业务项目目录注册 MCP 工具和事件级 plugin hook。

node /Users/ra/Downloads/Paper_Repo/Harmony_Evo/clients/harmony-evo-client/bin/harmony-evo-client.js install opencode --server http://localhost:3456 --upload-signals
默认只搜索和注入上下文。开启 --upload-signals 后上传事件级开发信号；只有再显式开启 --auto-submit 才会把高质量失败事件提交为候选案例。

事件级上传结构

上传的不是原始会话

客户端先脱敏、压缩、打分，只上传能支持审核和聚类的开发信号。

{
  "hook_event": "PostToolUseFailure",
  "kind": "post-tool-failure",
  "tool": {
    "name": "bash",
    "command": "npm run build 2>&1",
    "exit_code": 1,
    "has_stderr": false
  },
  "signals": ["hvigor_build_fail", "test_failure"],
  "search": {
    "top": [{

质量分来源

Claude Code 的失败事件表现为 PostToolUseFailure；OpenCode plugin 会把 opencode:tool-after 映射成同一种 post-tool-failure 信号。

证据作用
HarmonyOS 信号确认不是普通开发噪音。
工具失败证据exit code、stderr、失败 hook 事件提升可信度。
错误码或 exact match把事件和已有案例资产对齐。
脱敏风险发现密钥、cookie、password 会降权或隔离。

Hook 自进化原理

1. 捕获Claude/OpenCode hook 监听 prompt、工具调用、工具失败。
2. 脱敏本地移除 token、password、cookie、签名文件路径等。
3. 识别抽取 hvigor、权限、ArkUI、Ability、错误码等信号。
4. 检索用信号和错误文本查询服务端 DebugCase/Gene。
5. 注入把高相关案例作为上下文交给 Claude Code 或 OpenCode。
6. 打分上传按失败证据、匹配强度、上下文完整度生成 dev-signal。
7. 治理进化服务端审核、去重、归纳后进入案例库或 Evo Gene。

为什么要用 hook

只靠用户手动上传，案例缺少事件现场；只靠最终答案，又看不到失败命令和日志。Hook 能在事件发生时捕获“问题、工具、失败输出、命中案例、修复反馈”，这是生成高质量案例资产的最小证据链。

为什么不直接入库

开发事件是原材料，不等于案例。服务端先放入 dev-signals 或 submissions 队列，再通过审核、聚类、去重、LLM 结构化和反馈验证，才能进入正式 DebugCase 或 Evo Gene。

Gene / Capsule 真实生成链路

当前 Harmony_Evo 与 evolver-main 的桥接代码在 scripts/debug-case/inject.js 和 scripts/debug-case/promote.js。它不是把日志直接变成 Gene，而是先形成可审核的 DebugCase，再按复用次数、反馈和显式命令生成 GEP 资产。

1. DevSignalhook 事件级原材料，含失败证据、命中案例、质量分。
2. Submission高质量事件进入候选队列，等待审核、去重、LLM 结构化。
3. DebugCase正式案例落到 assets/debug_cases/cases.jsonl。
4. Candidate写入 evolver 的 candidates.jsonl，作为可被 GEP 读取的能力候选。
5. Gene复用次数达阈值或手动 promote 后，写入 genes.json。
6. Event每次 promotion/feedback 写入 events.jsonl，形成进化账本。
7. Capsule成功修复沉淀为可复用经验包，写入 capsules.json。

DebugCase -> Gene

caseToGene(dc) 会把案例里的症状、根因、修复方案和验证方法压缩成 Gene。真正写入发生在 promoteCase(dcId)： 

Gene {
  id: "gene_harmony_...",
  category: "repair" | "optimize",
  signals_match: [
    ...dc.symptom.error_signals,
    ...dc.tags.bug_type,
    dc.symptom.error_code
  ],
  preconditions: [
    "error matches one of: ...",
    "harmonyOS version in: ..."
  ],
  strategy: [
    dc.root_cause.analysis,
    dc.fix.description,
    "Key code: ...",
    "Validate: ..."
  ],
  constraints: { max_files: 5 },
  validation: ["echo \"...\""],
  _source: { kind: "harmony_debug_case", dc_id }
}

DebugCase -> Capsule

Capsule 记录的是“已经成功可复用的修复经验”。当前代码中 Capsule 不是自动由每次 feedback 生成，而是通过显式 injectAsCapsule(dcId) 写入： 

Capsule {
  id: "cap_harmony_...",
  summary: dc.title,
  category: dc.fix.strategy,
  signals: dc.symptom.error_signals,
  content: {
    problem: dc.symptom.scenario,
    analysis: dc.root_cause.analysis,
    solution: dc.fix.description,
    code: dc.fix.key_code_snippet,
    validation: dc.fix.validation
  },
  source: { kind: "harmony_debug_case", dc_id }
}
资产 当前生成机制 写入位置 作用
CapabilityCandidate injectAsCandidate(dcId) 或 promoteCase 时顺带写入。 ../evolver-main/assets/gep/candidates.jsonl 让 evolver 先看到可复用能力候选，但不等于正式 Gene。
Gene 案例 matched_count >= 3 后可 --auto promotion；也可 API 手动 promote。 ../evolver-main/assets/gep/genes.json 用于 GEP 选择器按 signals_match 选择修复策略。
EvolutionEvent promotion 和 feedback 都会写事件；feedback worked 是 reinforce，failed 是 revise。 ../evolver-main/assets/gep/events.jsonl 作为进化历史账本，记录来源、结果、分数和复用资产。
Capsule 当前需显式 injectAsCapsule(dcId)；已有 cap_harmony_001。 ../evolver-main/assets/gep/capsules.json 保存已验证经验包，给后续任务直接复用问题、分析、方案、代码和验证。
真实边界：当前已经有 Gene promotion、Candidate 写入、Feedback event、显式 Capsule 注入；还没有把 dev-signals -> DebugCase -> Capsule 完全自动化。合理的下一步是：用 LLM 对 dev-signals 聚类和结构化，人工审核后入 DebugCase；当 worked 反馈达到阈值时，再自动生成 Capsule。

推荐演示话术

“Harmony_Evo 的客户端不是简单的搜索插件。它在 Claude Code 和 OpenCode 的开发事件里捕获失败证据，先用本地脱敏保护隐私，再查询团队共享案例库，把最相关的修复经验注入当前开发会话。事件同时会形成 dev-signal，进入服务端审核队列，后续可由 LLM 归纳成新的 DebugCase；DebugCase 复用达到阈值后生成 Gene，成功修复经验再沉淀为 Capsule，最终成为 evolver 可选择、可复用、可追踪的 GEP 资产。”
