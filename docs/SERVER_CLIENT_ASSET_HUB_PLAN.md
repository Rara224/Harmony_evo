# Harmony_Evo 服务端资产中心与客户端 Hook 规划

日期：2026-05-25

## 结论

把 Harmony_Evo 改造成服务端资产中心是有意义的，也比继续把它做成本地工具更接近长期价值。

当前项目已经有 DebugCase schema、采集、提取、搜索、质量检查、evolver 资产注入和 Web API。它最欠缺的不是再加一个本地页面，而是把“个人踩坑经验”变成“可共享、可审核、可检索、可回流”的团队知识资产。

推荐方向：

- Harmony_Evo 主项目转为服务端：管理案例、基因、候选、反馈、权限、审核、去重、质量评分和分发。
- 客户端单独实现：Claude Code / Codex / IDE / CLI hook，负责本地错误捕获、脱敏、查询服务端资产、注入上下文、记录反馈、上传候选案例。
- 服务端不直接介入用户本地代码修改；客户端不默认上传原始日志和代码。两边职责必须分开。

这个架构比“所有逻辑都塞进本地 hook”更稳，因为共享资产需要中心化治理，而本地开发上下文又必须留在客户端侧处理隐私和环境差异。

## 为什么这个方案成立

### 1. 案例资产天然需要中心化

HarmonyOS 问题有强复用价值：权限、Ability、ArkUI、Hvigor、签名、设备兼容、API 版本差异，很多问题不是项目独有，而是生态共性坑。

如果只存在本地：

- 每个人重复踩坑。
- 每台机器的案例质量不同。
- 好案例无法审核、合并、纠错。
- 命中和修复反馈无法形成可信统计。

放到服务端后，可以做：

- 团队共享搜索。
- 跨项目去重。
- 版本化案例资产。
- 修复成功率统计。
- 低质量案例降权。
- 高价值案例升级为 Gene / Capsule。

### 2. Hook 客户端天然需要本地化

开发过程中的错误、日志、diff、用户 prompt、构建输出、测试结果都在本地。它们可能包含：

- token、账号、签名密码。
- 私有包名、业务域名、内部接口。
- 未公开代码。
- 用户真实业务日志。

所以客户端应该先在本地完成：

- 错误信号提取。
- 脱敏。
- 与服务端检索交互。
- 是否上传的用户确认或策略判断。
- 将服务端返回的资产注入 Claude/Codex/IDE 上下文。

服务端只应该拿到“最小必要信息”和“已脱敏的候选资产”。

### 3. 当前代码已经具备服务端雏形

现状已有：

- `assets/debug_cases/cases.jsonl`：正式案例库。
- `assets/debug_cases/candidates/*.jsonl`：原始候选。
- `schemas/debug-case.schema.json` 和 `scripts/debug-case/schema.js`：数据约束。
- `scripts/debug-case/search.js`：本地检索。
- `server/index.js`：REST API 和 Dashboard。
- `scripts/debug-case/promote.js` / `inject.js`：DebugCase 到 evolver Gene/Candidate/Capsule 的桥。

也就是说，第一版服务端不是从零开始，而是把当前本地文件式资产管理升级为多客户端可访问的资产 Hub。

## 目标形态

```text

                │       Harmony_Evo Server      │
                │  资产库 / 搜索 / 审核 / 分发   │
                └───────────────┬──────────────┘
                                │
       ┌────────────────────────┼────────────────────────┐
       │                        │                        │
┌──────▼──────┐         ┌───────▼───────┐        ┌───────▼───────┐
│ Claude Hook │         │ Codex Client  │        │ IDE / CLI     │
│ 本地捕获     │         │ 本地查询/上传  │        │ 本地提示/检索  │
└──────┬──────┘         └───────┬───────┘        └───────┬───────┘
       │                        │                        │
       └──────────── local project context ──────────────┘

本地：捕获、脱敏、查询、注入、反馈
服务端：存储、去重、审核、质量评分、资产分发、统计
```

## 资产类型

服务端不应该只存 DebugCase。建议抽象成几类资产：

| 资产 | 作用 | 当前项目对应物 |
| --- | --- | --- |
| DebugCase | 具体问题、根因、修复、验证 | `cases.jsonl` |
| RawCandidate | 未结构化候选来源 | `candidates/*.jsonl` |
| Gene | 可被 agent 复用的策略单元 | `genes.json` |
| Capsule | 多次成功/失败后的经验总结 | `capsules.json` |
| FeedbackEvent | 命中、成功、失败、误报 | `events.jsonl` / `system_metrics.jsonl` |
| RedactionRule | 脱敏规则和风险策略 | 目前缺失 |
| ProjectProfile | 技术栈、HarmonyOS 版本、依赖、设备环境 | 目前缺失 |

DebugCase 是入口资产，Gene/Capsule 是进化资产，FeedbackEvent 是质量资产。

## 服务端职责

服务端应该做资产治理，不应该做本地开发代理。

核心职责：

- 存储正式案例、候选案例、反馈事件、Gene、Capsule。
- 提供检索 API：错误码、信号、关键词、API 类别、HarmonyOS 版本、向量语义。
- 提供上传 API：接收已脱敏候选、人工案例、修复反馈。
- 提供审核流：submitted、reviewing、published、quarantined、rejected。
- 提供去重和聚类：同一报错、同一 API、同一根因合并。
- 提供质量评分：置信度、成功率、来源可信度、最近有效性。
- 提供资产分发：客户端按项目技术栈拉取相关资产。
- 提供导入导出：保留 JSONL 包能力，便于离线和迁移。

不建议服务端做：

- 直接读取用户本地项目。
- 直接运行用户本地命令。
- 直接替用户修改代码。
- 默认保存原始未脱敏日志。

## 客户端职责

客户端是 hook 和本地上下文适配层。

核心职责：

- 监听开发会话、用户 prompt、工具结果、构建输出、测试结果。
- 从本地错误中抽取信号：错误码、组件名、API、堆栈、关键词、HarmonyOS 版本。
- 本地脱敏：token、账号、签名、路径、业务域名、私有包名、日志中的用户数据。
- 查询服务端，获取 Top N 相关资产。
- 将少量高置信资产注入 agent 上下文，避免污染上下文。
- 在用户确认或策略允许时上传新候选案例。
- 记录修复反馈：命中是否有用、是否解决、是否误导。
- 保留本地缓存，服务端不可用时仍能搜索最近资产。

客户端可以有多个实现：

- Claude Code hook。
- Codex hook 或 CLI。
- DevEco Studio / VSCode 插件。
- 纯命令行 `harmony search`。

## 推荐链路

### A. 解决问题时拉取资产

```text
开发者遇到报错
→ 客户端从 prompt / terminal / test output 提取信号
→ 本地脱敏
→ 请求服务端搜索
→ 服务端返回 DebugCase / Gene / Capsule
→ 客户端选择 Top 3 注入 agent 上下文
→ agent 给出修复建议
→ 用户或测试结果反馈是否有效
→ 客户端回传 FeedbackEvent
```

关键点：服务端返回的不是长篇知识库，而是短、可信、可执行的资产摘要。否则会拖慢 agent 并增加误导。

### B. 新案例自进化并上传

```text
本地问题未命中服务端
→ agent / 用户解决问题
→ 客户端从错误、diff、验证结果中生成本地候选
→ 本地脱敏和压缩
→ 用户确认或策略自动提交
→ 服务端进入 submitted
→ 服务端 LLM/规则补全结构化字段
→ 去重/聚类/审核
→ 发布为 DebugCase
→ 多次命中和成功反馈后升级为 Gene/Capsule
```

关键点：上传的第一状态应该是候选，不应直接发布。否则共享资产很快会被噪音污染。

### C. 资产回流到本地

```text
客户端启动
→ 上报项目 profile：HarmonyOS 版本、API level、依赖、设备类型
→ 拉取相关资产包
→ 本地缓存
→ 开发中优先本地命中，必要时远程补查
```

关键点：不要每次 prompt 都远程请求完整库。应该缓存、增量同步、按项目 profile 分发。

## 搜索和排序原则

服务端排序应该混合多种信号：

1. 硬匹配：错误码、API 名、组件名、异常名。
2. 信号匹配：`permission_dialog_not_show`、`canvas_issue`、`hvigor_build_fail`。
3. 语义匹配：中文描述、日志片段、场景相似度。
4. 项目匹配：HarmonyOS 版本、API level、设备、DevEco/Hvigor 版本。
5. 质量权重：人工审核、来源可信、成功反馈、最近有效。
6. 反例降权：多次反馈无效、版本不适用、被标记误导。

当前项目主要是 1、2、3 的简单版本；服务端化以后，4、5、6 才是核心差异。

## 脱敏和安全

这是最重要的工程边界。

上传前必须做客户端本地脱敏：

- API Key、token、cookie、authorization header。
- 证书路径、签名密码、keystore 信息。
- 私有域名、内网 IP、业务接口。
- 包名、AppID、BundleName，可按策略保留哈希。
- 用户手机号、邮箱、身份证、订单号等日志数据。
- 大段源码默认不上传，只上传最小必要片段。

服务端还要做二次脱敏和风险扫描。高风险候选进入 quarantine，不进入共享检索。

推荐策略：

- 默认上传结构化摘要，不上传原始全文。
- 原始日志只保存在本地，除非用户明确选择。
- 服务端保留 redaction report，方便审核知道删掉了什么类型的信息。
- 所有共享资产记录 provenance：来源、上传者、时间、脱敏版本、审核状态。

## 权限和共享边界

服务端至少需要三层空间：

- Personal：个人私有资产。
- Team：团队共享资产。
- Public/Internal Hub：更大范围共享资产。

权限模型建议：

- viewer：只能搜索和使用。
- contributor：可提交候选和反馈。
- reviewer：可审核、合并、发布。
- admin：管理租户、规则、黑名单和导出。

不要一开始就做复杂组织系统，但数据模型要预留 `tenant_id`、`visibility`、`owner`、`review_status`。

## 数据存储建议

短期可以保留 JSONL 导入导出，但服务端主存储不建议继续只用 JSONL。

推荐：

- MVP：SQLite + 本地文件对象存储。
- 团队部署：Postgres + 对象存储。
- 语义检索：先用轻量向量索引，后续接 pgvector 或专用向量库。
- JSONL：作为备份、导出、离线同步格式保留。

原因：

- 共享上传需要事务、审核状态、版本、权限和并发写入。
- JSONL 适合本地 append，不适合作为多人服务端主库。
- 资产回滚和合并需要可查询的版本关系。

## 与 evolver 的关系

服务端不应该直接假设每个客户端都有 `../evolver-main`。

更合理的关系是：

- 服务端保存标准资产：DebugCase、Gene、Capsule、Feedback。
- 客户端根据本地工具链把服务端资产转换成本地可用格式。
- 如果本地有 evolver，则客户端把相关 Gene/Capsule 注入本地 evolver。
- 如果本地没有 evolver，则客户端只把 DebugCase 摘要注入 Claude/Codex 上下文。

也就是说，evolver 是一种消费者，不是服务端唯一目标。

## 分阶段规划

### Phase 0：协议稳定

目标：先定义共享资产协议，不急着做复杂服务。

- 固化 DebugCase v1 schema。
- 增加共享字段：visibility、review_status、provenance、redaction、license、quality_score。
- 定义客户端上传包格式。
- 定义服务端返回资产摘要格式。
- 当前 JSONL 数据可无损导入。

验收：

- 能把现有 187 条 case 导出为共享包。
- 能导入共享包并保持 ID、来源、质量信息。

### Phase 1：服务端 MVP

目标：把当前本地 Dashboard 升级成团队资产服务。

- 服务端持久化从 JSONL 升级到 SQLite。
- 支持搜索、详情、候选提交、反馈提交。
- 支持审核状态：submitted / published / rejected / quarantined。
- 支持简单 token 鉴权。
- 支持导入现有 `cases.jsonl` 和 candidates。
- 支持服务端质量报告。

验收：

- 多个客户端可以查询同一服务端。
- 客户端可以上传候选，不直接污染正式案例库。
- 审核后案例进入正式搜索。

### Phase 2：Hook 客户端 MVP

目标：让真实开发会话能用服务端资产。

- Claude Code hook 客户端读取本地错误信号。
- 本地脱敏后请求服务端。
- 将 Top 3 资产注入上下文。
- 会话结束或测试通过后回传反馈。
- 支持本地缓存。

验收：

- 遇到 HarmonyOS 报错时，不打开网页也能拿到相关案例。
- 命中使用后能自动记录反馈。
- 未命中但已解决的问题能生成候选并上传。

### Phase 3：质量和智能化

目标：解决共享资产会变脏的问题。

- LLM 结构化提取替代模板提取。
- LLM 辅助脱敏、归因、去重、聚类。
- embedding 语义检索。
- 根据成功率和版本适用性排序。
- 低质量资产自动降权。
- 冲突案例提示 reviewer 合并。

验收：

- 搜索结果不是“多”，而是“准”。
- 无效反馈会降低资产曝光。
- 同一问题不同表述能聚合。

### Phase 4：企业化共享

目标：多人、多团队、长期运行。

- 租户和团队权限。
- 审核队列和责任人。
- 审计日志。
- 资产版本和回滚。
- 黑名单和撤回。
- CI/定时采集。
- IDE 插件。

验收：

- 可以作为团队内部 HarmonyOS DebugCase Hub 长期运行。
- 能控制隐私、版权和误导风险。

## 当前项目应该怎么调整方向

推荐把当前 repo 改成三块：

```text
Harmony_Evo/
  server/              # 资产中心服务端和管理台
  schemas/             # 共享协议和 schema
  scripts/             # 迁移、导入导出、采集、质量任务
  clients/             # 后续可放轻量客户端样例，但主客户端可独立仓库
  assets/              # 开发/种子数据，不再作为唯一主存储
```

短期不要重写所有东西。更稳的路径是：

1. 保留当前 Express Dashboard。
2. 增加服务端资产概念和审核状态。
3. 把 JSONL 当 seed/import/export。
4. 先做一个最小 Claude Code 客户端，验证“开发中请求服务端资产”。
5. 再做上传闭环。

## 主要风险

### 数据质量风险

共享上传会带来大量半成品、误判和重复案例。必须有审核、去重、反馈降权。

### 隐私风险

客户端 hook 最容易误传敏感信息。必须本地脱敏优先，服务端二次扫描。

### 上下文污染风险

返回太多案例会干扰 agent。客户端只应注入少量高置信资产。

### 版本适用风险

HarmonyOS API、DevEco、Hvigor 版本差异明显。案例必须带版本和环境，否则容易误导。

### 自动化过度风险

不要一开始就自动发布、自动改代码、自动提升 Gene。先让系统做到“推荐准确、反馈可信”，再提高自动化程度。

## 最小可行产品

MVP 只做四件事：

1. 服务端统一管理 DebugCase，并支持搜索。
2. 客户端 hook 能把本地错误脱敏后查服务端。
3. 服务端能接收候选上传，但默认进入审核队列。
4. 客户端能回传“有用/无用/解决/未解决”的反馈。

不做：

- 不做完整 IDE 插件。
- 不做复杂组织权限。
- 不做自动代码修复。
- 不做未经审核的公开共享。
- 不做服务端读取用户本地项目。

这个 MVP 足够验证核心价值：共享资产是否真的能提高开发修复效率。

## 推荐下一步

1. 先定义 `SharedDebugCase` 和 `AssetEnvelope` 协议。
2. 把现有 187 条案例作为服务端 seed 数据持续治理。
3. 在已有 submissions/dev-signals API 上补完整审核工作台。
4. 扩展 Claude Code / OpenCode hook 客户端：加入反馈聚合、项目 namespace 和更细粒度脱敏策略。
5. 用 1-2 个真实 HarmonyOS 项目长期试运行，重点观察命中率、误报率、上传质量和脱敏风险。

最终判断：这个方向可行，而且比单机版更值得做。但成功关键不是“多接几个 hook”，而是服务端资产治理能力：去重、审核、质量排序、隐私控制、反馈闭环。没有这些，共享库会很快变成噪音库；做好这些，它才会变成真正的团队级 HarmonyOS 经验资产中心。
